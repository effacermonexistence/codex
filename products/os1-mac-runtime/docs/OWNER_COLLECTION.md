# Source-bound independent owner collections

This is a bounded **non-statistical R0 task-contract extension**, not P7 trained evidence, a new coordinator, or proof of generic semantic decomposition.

An optional `PreparedTaskQuality.Envelope.ownerCollection` names 2–8 independent read-only obligations. Every instruction is an unmodified, ordered, disjoint UTF-8 span of the original user request. Each record includes an ID, relative source paths and exact source hashes. v1 requires the parent's existing `localEffectsOnly` native isolation, so the catalog keeps only fresh Codex execution in the reviewed local profile. Claude's persisted record currently has no owned turn ID and cannot borrow this control proof. The parent and **each child instruction** must have separate, pre-registered FULL owner contracts with independently frozen checkers, matching request/context/source/start-tree/policy, current validity and no reference-score/gold-derived adoption.

The original owner request and necessary context still travel in every native child envelope. A source file is evidence, not a control-plane instruction. Declared source paths do not grant extra filesystem permission. The existing native scope, source confinement, account and cancellation contracts remain authoritative.

## Execution

1. Native catalog privately reopens the original parent contract and every exact child contract; source bytes, UTF-8 spans, checker identity and validity are rechecked.
2. Only the resulting strict `task_contract.owner_collection` fact can activate the family. The local LLM cannot mint it or promote partial evidence. Existing seven partial contracts are not rewritten.
3. The same Core can deterministically create the already owner-specified partition, avoiding an unnecessary planning-model call. This path does not pretend that an LLM autonomously understood arbitrary prose.
4. Every child is bound through existing R0 exact-row selection and its independently checked cheap result retains one prebound native reference fallback. A different child's FULL result cannot certify this child. After the same native adapter returns, `rcc-owner-control` checks the exact stored native record/witness/profile and owned turn before Core can adopt the child as FULL. Unknown protocol or control evidence becomes typed HOLD with raw child artifacts retained, **not** an automatic reference retry. The shared finally path records real usage exactly once and releases only actually terminated read-only reservations; restart never replays held work.
5. Existing one-parent scheduler/worker/pool reservations execute independent children concurrently where current capacity and permission permit. There is no adapter/UI retry owner.
6. Only JSON objects are collected. Core preserves their declared order in one JSON array, without labels, summarizing LLM or invented integration task.
7. The existing plugin returns that same task to a read-only native `rcc-task-verify` operation. It rereads actual private native child records and their operational witnesses, then verifies a bounded known Codex rollout grammar for the exact native turn (`task_started` → `task_complete`, matching final bytes, zero tool/custom-tool/delegation events). Unknown format, missing terminal evidence, partial lines, malformed data and source races fail closed; EOF or a zero summary count is not proof. Only the recorded turn's own file is read, never global transcript search. It checks original task/source/policy/account/instruction/configuration/checker bindings, reruns the independently frozen FULL parent checker and rechecks current authority/source state. The parent receipt says **Core collection**, not a fabricated native/model turn. Only this exact finite contract may become task-verified; parity remains unverified.
8. Parent-check failure preserves the candidate output as unverified. Revoked or changed authority before dispatch holds rather than adopting a different plan or silently discarding completed artifacts.

## Optionality / resource boundary

No collection field means original behavior. A low parallel budget (<2), insufficient per-node attempt budget (<2), or explicit native dispatch cap below 2N keeps the original one-node R0 alternative. The existing hard-zero model-generation policy wins before the catalog or any opaque callback. This source does not create a registry or turn on general planning.

`ownerCollection` is an explicit host pre-registration choice, **not proof that N calls cost less**. Two children repeat the base instructions and original request, so their total tokens may exceed one maximum-reference call. Records retain `host_owner_collection_v1`, the original single-parent alternative, all actual calls/usage/latency and failed attempts. Parallel-feature proof, task correctness and resource savings must be measured separately. No generic quota-halving or strongest-model parity is claimed by this implementation or its synthetic fixtures.

## Registration shape

The trusted parent envelope gains this optional camelCase object:

```json
{"ownerCollection":{"schema":1,"kind":"independent_readonly_json_v1","obligations":[{"id":"source_a","instruction":"<exact original owner span>","requestUTF8Start":123,"requestUTF8End":456,"sourcePaths":["a.txt"],"sourceSHA256s":["<host verified SHA-256>"]}]}}
```

The example is schema-only (real contracts require 2–8 records). Child contracts remain in the existing private `contracts/sha256(childInstruction).json` namespace, not model-visible planning data. The existing parent contract's own checker verifies the complete array. Catalog facts use strict snake_case wire keys and add the exact child contract/checker IDs; they contain no expected answers.

## Validation boundary

Node and Swift fixtures are explicitly **synthetic source/fake-backend regressions, not actual quality evidence, live activation, training or public proof**. A controlled real comparison must freeze its original sources, owner spans, private independent checkers, policy and budget before generation. A model-produced `complete`, schema-valid DAG, matching requirement label, synthetic quality percentage, repeated answer or passed generic unit suite cannot supply this capability.
